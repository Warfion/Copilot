# Git Commit & Push

A safe, repeatable workflow for committing and pushing changes in **any** repository.
Follow every step in order. Never skip the confirmation gate.

## Operating principles (non-negotiable)

1. **Confirm before writing.** Always show the user the staged files and the exact
   proposed commit message, and wait for explicit approval before running `git commit`.
   Never commit and push in a single unattended action.
2. **Stage selectively.** Review the working tree and stage only files that belong to
   this change. Exclude unrelated edits, in-progress scratch files, secrets, build
   artifacts, and anything the user didn't intend. Never blindly `git add -A` without
   review.
3. **Respect git hooks.** Never use `--no-verify`. If a pre-commit or pre-push hook
   fails, STOP, show the hook output, and let the user fix the underlying problem.
4. **Never force-push.** If a push is rejected because the remote is ahead, STOP and
   report. Do not run `git push --force` / `--force-with-lease` or auto-rebase. The
   user decides how to reconcile.
5. **Protected-branch guard.** If the current branch is `main` or `master`, warn the
   user and require an explicit "yes" before committing there.
6. **Clean messages.** No "Generated by Copilot", no `Co-authored-by`, no tool footer.
7. **Auto-set upstream.** If the current branch has no upstream, push with
   `git push -u origin <branch>` to the same-named remote branch.

## Workflow

### 1. Inspect the working tree
Run these read-only commands and summarize for the user:
```
git rev-parse --abbrev-ref HEAD      # current branch
git status --short                    # changed/untracked files
git diff --stat                       # scope of unstaged changes
```
If there are no tracked, staged, or untracked changes to commit, tell the user and stop.
If files are already staged from a prior session, show them and ask the user whether to
include them, reset them, or abort before proceeding.

### 2. Protected-branch check
If the branch is `main` or `master`, warn:
> ⚠️ You're on `main`. Commit directly to it? (yes/no)

Stop until the user confirms. If they say no, ask which branch to use (do not create or
switch branches unless asked).

### 3. Select and stage files
- Group the changes logically and decide which files belong to this commit.
- Call out anything suspicious you are deliberately leaving out (unrelated edits,
  `*.env`, secrets, large artifacts, in-progress files).
- Stage explicitly by path:
```
git add <path1> <path2> ...
```
- Re-show `git status --short` so the user sees exactly what is staged.

### 4. Draft the commit message (Conventional Commits)
Format: `type(optional-scope): summary`
- **Types:** `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `perf`, `build`, `ci`, `style`, `revert`.
- Summary: imperative mood, ≤ ~72 chars, no trailing period.
- Add a body (`-m` second paragraph) when the change needs context: what and why.
- Breaking change → add `!` after type/scope and a `BREAKING CHANGE:` footer.
- No AI/tool trailers.

Present the proposed message to the user verbatim.

### 5. Confirmation gate (mandatory)
Show:
- the staged file list, and
- the exact commit command that will run.

Wait for explicit approval. If the user edits the message, use their version.

### 6. Commit
```
git commit -m "type(scope): summary" -m "optional body"
```
If a hook fails: STOP, show output, do not retry with `--no-verify`.

### 7. Push
- If the branch has an upstream:
```
git push
```
- If it has no upstream:
```
git push -u origin <current-branch>
```
- If the push is **rejected** (remote ahead): STOP and report. Show the rejection and
  suggest the user pull/rebase manually. Never force-push.

### 8. Report
Confirm the commit hash, branch, and that the push succeeded (or exactly where it
stopped and why).

## Quick reference
| Situation | Action |
|-----------|--------|
| No changes | Report and stop |
| On `main`/`master` | Warn, require explicit yes |
| Unrelated/secret files present | Exclude from staging, mention it |
| Hook fails | Stop, show output, no `--no-verify` |
| Push rejected (remote ahead) | Stop, report, never force-push |
| No upstream | `git push -u origin <branch>` |
